# Load test results — 2026-10-03 (BACKLOG 20.29)

Operator targets: "the pipeline holds if there are multiple requests for video creation" and
**200 concurrent users**. Everything below ran on GitHub Actions with **simulated providers**
(`STUDIO_FAKE_PROVIDERS=1`): no production system was touched and no paid API was called. How to
run it again: `runbooks/load-testing.md`. Raw data: the artifacts of the "Load test" workflow
runs 37124580010, 37132870114 and 37138242955 (branches `load-test/api-1`, `load-test/api-2`,
`load-test/full-2`).

## Verdict

| Question | Answer |
| --- | --- |
| Does the current server hold 200 concurrent users? | **Yes, once the containers get the 4 GB sizing** (below). With today's container limits (the 2 GB defaults) it serves them **without errors but too slowly**: read p95 178–666 ms against the 300 ms objective, and the web container peaks at 405 of 448 MiB, one spike from being OOM-killed. With the 4 GB sizing: read p95 59–120 ms, page p95 59–100 ms, 0 errors in 94,000 requests, every container under 60 % of its limit. Production only: production and staging together do not fit in 4 GB. |
| Does the pipeline hold many simultaneous "generate"s? | **Yes**: 100 videos started in the same second all reached review in every run (0 failures from rate limits or concurrency), the provider caps and per-organisation shares were never exceeded, and every waiting project showed "Queued: … will start soon". Before this change the same burst produced 53–133 provider 429s per 50 videos and spilled onto dearer providers. |
| How fast are videos made? | Limited by the **video provider account, not the server**: ~24 STANDARD 30 s videos an hour on the individual BytePlus (Seedance) account (3 clips at once), whatever the server size. 100 at once: last one ready after ~4 h. 200 users each pressing generate once: ~8 h to clear. |
| What fixes that? | A **BytePlus enterprise account** (10 concurrent): ~56 videos an hour, 100 at once done in ~1¾ h, same cost. Or `STUDIO_PROVIDER_OVERFLOW=failover` today: ~66 an hour, ~25 % dearer per video (Kling takes the overflow). |

## What was built and fixed

1. **Per-provider in-flight caps** (`providers/provider-concurrency.ts`): a Redis semaphore per
   provider account, Seedance 3 and Kling 20 by default (`STUDIO_PROVIDER_CONCURRENCY_<ID>`), with a
   fair share per organisation (half the slots, rounded up: one organisation can never take the
   whole account). A job that finds the provider full is **delayed, not failed** (no retry spent);
   waiters are counted so retries slow down (10–20 s, up to 6×) when the queue is long.
2. **Provider "too many requests"** (HTTP 429, Kling 1302/1303, Gemini `RESOURCE_EXHAUSTED`) delays
   the job with jittered back-off up to 8 times (~10 min) instead of spending the job's 6 attempts in
   ~2.5 min (`queue/rate-deferral.ts`).
3. **Overflow policy** `STUDIO_PROVIDER_OVERFLOW=queue|failover` (default queue = cheapest).
4. **"Queued" state for customers**: `metadata.providerWait` on the project; the project page shows
   "Queued: lots of videos are being made right now, so yours is waiting its turn and will start
   soon. You don't need to do anything." (11 languages).
5. **Sizing** for the 4 GB server in `deploy/vps/.env.example` (below), measured.
6. The harness, the 200-user k6 scenario, the workflow, the runbook.

## 200 concurrent users (k6, `load-test/k6/studio-users.js`)

200 users ramping up over 2 minutes, holding for 6: dashboard, project, library, calendar,
analytics and page loads, creating projects and generating (2 % of actions), 3–8 s think time,
plus 100 users pressing "generate" in the same second 3 minutes in. About 57 requests a second.
Production compose stack (`deploy/vps/compose.yml`) with its container limits; the worker
container processed the generated videos at the same time. Three runs per sizing; ranges show
the spread between runs (CI runners are shared machines).

| p95 (ms) | Current limits (2 GB defaults) | 4 GB sizing |
| --- | --- | --- |
| Reads (`/api/studio/*` GET) | 178 – 666 | **59 – 120** |
| Pages (server-rendered) | 148 – 452 | **59 – 100** |
| Writes (create project) | 442 – 1,301 | **222 – 358** |
| Generate | 1,497 – 2,351 | **317 – 902** |
| Errors | 0 | 0 |
| 429 from the API's own rate limits | 0 | 0 |

| Peak (of limit) | Current limits | 4 GB sizing |
| --- | --- | --- |
| web | 393–405 MiB of 448 MiB, CPU 88–108 % | 472–480 MiB of 1 GiB, CPU 124–157 % |
| worker (with FFmpeg) | 345–612 MiB of 704 MiB | 370–726 MiB of 1.25 GiB |
| postgres | 141–166 MiB of 384 MiB, ≤ 17 connections | 226–252 MiB of 768 MiB, ≤ 32 connections of 60 |
| redis | 26–36 MiB (maxmemory 64 MB) | 30–32 MiB (maxmemory 128 MB) |

Bottlenecks found: the **web container's memory and CPU** (448 MiB / 1 CPU) and the **worker's
memory** (704 MiB with FFmpeg). The database pool was never short (no Prisma pool timeouts) and
Redis used half its memory with ~400 videos queued. No caching change was needed: reads that hit
Postgres stayed under 120 ms at p95 once the web container had the CPU.

## Video bursts (pipeline harness, `scripts/load/pipeline-load.ts`)

Real pipeline (BullMQ on Redis 7, Postgres 17, real FFmpeg probe/blackdetect/loudness/mastering on
sample media), simulated providers with real-provider behaviour: AI clips 30–180 s, Shotstack
20–60 s, Seedance 3 / Kling 20 / Veo 10 concurrent tasks per account with 429 over it, 5 % random
429s and 2 % failed generations. STANDARD 30 s shorts (4 AI clips each), half the burst from one
"heavy" organisation. Times are real-time equivalents (the run is 10× faster). Last run (37138242955):

| Scenario | Ready | Time to ready p50 / p95 | Videos / hour | Cost / video p50 | Notes |
| --- | --- | --- | --- | --- | --- |
| 10 at once, 2 GB sizing | 10/10 | 27 / 36 min | 16.5 | 112p | |
| 25 at once, 2 GB sizing | 25/25 | 62 / 84 min | 17.4 | 112p | |
| 50 at once, 2 GB sizing | 32 + 18 paused | 102 / 128 min | 14.8 | 112p | heavy org hit its £15 STANDARD daily cost cap: the guard working |
| 50 at once, 4 GB sizing | 27 + 23 paused | 87 / 100 min | 15.8 | 112p | same |
| 50 at once, caps off (before 20.29) | 27 + 23 paused | 29 / 49 min | 23.9 | 123p (max 160p) | 133 provider 429s; Seedance breaker opened, overflow to Kling |
| **100 at once (40 orgs), queue** | **100/100** | 209 / 247 min | 24.0 | 116p | all 100 showed "Queued" |
| 100 at once, failover | 100/100 | 52 / 90 min | 65.8 | 145p (max 160p) | Kling takes the overflow |
| 100 at once, **Seedance enterprise (10)** | 100/100 | 77 / 106 min | 55.9 | 112p | |

- **Caps held in every run**: Seedance peak in flight 3/3 (10/10 enterprise), one organisation at
  most 2 of 3 (5 of 10). No shot failed on a rate limit or concurrency error.
- **Fairness**: no organisation was starved (every light organisation finished), but slots go to
  whichever waiter asks first after one frees, not strictly first-come: the slowest light
  organisation's median was 1.2–7× the fastest's. To favour many small organisations over one big
  one on the individual account, set `STUDIO_PROVIDER_CONCURRENCY_SEEDANCE=3,org=1`.
- **Throughput ceiling** = account slots ÷ AI-clip time: 3 slots × 3,600 s ÷ (4 clips × ~105 s) ≈ 26
  videos an hour; measured 24. The server is not the limit (worker CPU ≤ 124 % of one process,
  ≤ 2 FFmpeg children, ≤ 12 database connections).
- **Cost guard**: organisations that started 25 videos in a day were paused at the STANDARD daily
  cap (£15) with "resumes after midnight", as designed; the 200-user runs paused 72–103 videos the
  same way (k6 users generate far more than real ones).

## Recommendations

1. **Apply the 4 GB sizing now** (`deploy/vps/.env.example`, the commented block): web 1 GiB / 1.5 CPU
   / heap 640 MB / pool 15; worker 1.25 GiB / 1.5 CPU / heap 512 MB / pool 15, orchestration 4,
   assets 12, FFmpeg 2; Postgres 768 MiB, shared_buffers 192 MB, max_connections 60; Redis 192 MiB,
   maxmemory 128 MB. Run staging elsewhere, or only while testing.
2. **Ask BytePlus for an enterprise account** (10 concurrent, 600 RPM), then set
   `STUDIO_PROVIDER_CONCURRENCY_SEEDANCE=10`: video throughput goes from ~24 to ~56 an hour at the
   same cost per video. Kling's single video pack (20 concurrent) is enough as the second provider.
   Veo's limits come from the Google AI Studio project's quota page: set
   `STUDIO_PROVIDER_CONCURRENCY_VEO` to it if Veo becomes a main provider.
3. Keep `STUDIO_PROVIDER_OVERFLOW=queue` (cheapest) unless waiting hours is worse than ~25 % more
   cost per video during bursts; `failover` is a one-line switch.
4. **When to scale the server**: when staging must run beside production, or the web container
   passes ~80 % of its memory, or read p95 passes 300 ms, or users go well past 200. Options
   (Hetzner, EU, excl. VAT, read 2026-10-03): **CPX32** 4 vCPU / 8 GB / 160 GB, **€35.99 a month**, the
   whole stack with headroom for staging; or keep this server and add a **CPX22** 2 vCPU / 4 GB
   (**€19.99 a month**) for the worker (`STUDIO_WORKER_QUEUES` split, already supported). Managed
   Postgres / Redis are **not needed** at this load (Postgres peaked at 252 MiB and under one CPU);
   the smallest managed plans (e.g. DigitalOcean, 1 vCPU / 1 GB) are about $15 a month each.
5. Watch the queue: `studio_jobs_total{outcome="deferred"}` and the assets queue's delayed count
   show provider waits; a long queue means the provider account, not the server, needs raising.

## Phase 2 — a small real-provider burst on production (proposed, NOT run)

Five 30-second STANDARD shorts started at once for an organisation the operator owns, on the live
server, through the normal worker. It confirms the simulated timings, the Seedance cap of 3 and the
"Queued" note with real providers.

```bash
# after this branch is merged and deployed; on the server:
scripts/vps/compose.sh production run --rm ops node --import tsx scripts/load/real-burst.ts \
  --org <your organisation id> --business <its business id> --videos 5 --confirm-spend-pence 2000
```

- **Expected cost £7–10**: the 20.25 cost model puts a STANDARD short at ~141p with Seedance (5 ×
  141p ≈ £7.05), up to ~153p each if Kling takes some clips; retries can add a little. **Hard cap
  £20**: each project's budget is 400p and the script refuses to start unless
  `--confirm-spend-pence` covers 5 × 400p.
- **Expected time**: ~25–35 minutes for all five (3 clips at once on the individual account).
- The organisation needs a plan with full access and room under its daily cost cap (the operator's
  organisation is on a PLUS trial with a £15 total cap: raise it in Admin first).
