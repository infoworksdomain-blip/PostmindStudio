> **Not the primary path any more.** The operator dropped Render for cost (about $536/month for
> staging + production) in favour of one Hetzner server: follow [vps-deploy.md](vps-deploy.md).
> `render.yaml` and `scripts/render/*` are kept, still validated in CI
> (`test/unit/render-blueprint.test.ts`, the Blueprint JSON Schema check), so Render remains a
> ready alternative, for example if the product outgrows one server and managed Postgres is wanted.

## What the Blueprint creates

One Render **project** `postmind-studio` with two **environments**, all in region **frankfurt**:

| Resource (per environment) | Render type | Notes |
| --- | --- | --- |
| `studio-db-<env>` | Postgres 17 | pgvector is enabled by the first migration. Private network only. |
| `studio-kv-<env>` | Key Value (Valkey 8) | `noeviction` (BullMQ needs it), journal + snapshot persistence, no external access. Studio uses DB 3. |
| `studio-web-<env>` | Web service (Docker) | Next.js on port 3010. Before each deploy: `prisma migrate deploy` + the idempotent seed. Health check `/api/health/ready`. |
| `studio-worker-<queue>-<env>` ×6 | Private service (Docker) | One per queue: orchestration, assets, publish, scheduled, analytics, library. Private services (not background workers) so Prometheus can scrape `:9464/metrics`. |
| `studio-monitoring-<env>` | Private service + 5–10 GB disk | Prometheus, Alertmanager, blackbox exporter. Pages via PagerDuty, tickets to Slack. |
| `studio-backup-storage-<env>` | Cron job (Docker), daily 03:30 UTC | Backup copy of the assets, renders and thumbnails buckets into the backup bucket; copies whose source was deleted age out after 30 days ([backup-recovery.md](backup-recovery.md)). No database. |
| `studio-config-<env>` | Environment group | Non-secret settings, kept in git. |
| `studio-metrics-<env>` | Environment group | `METRICS_TOKEN`, generated by Render. |
| `studio-secrets-<env>` | Environment group | **Empty until you fill it in step 4.** |

Staging deploys `main` automatically once CI passes. Production never deploys on its own: you promote
a commit that passed on staging (step 8).

**Cost** (Render list prices): staging about **$124/month**, production about **$387/month**, plus
the Pro workspace at $25/month, bandwidth over 5 GB at $0.15/GB and build minutes. The breakdown
is at the top of `render.yaml`.

### Why the secrets live in one group

A Blueprint can ask for a secret (`sync: false`) only on a service, not in an environment group,
and only when the Blueprint is first created. Studio has seven services that need the same ~30
secrets, so prompting per service would mean pasting each one seven times. Instead every app
service links `studio-secrets-<env>`, and you paste the secrets **once per environment** into that
group. Rotating a secret is one edit there. Render keeps environment variables that the Blueprint
does not list, so a later Blueprint sync leaves them alone (verify this after your first sync, step 7).

### Not on Render

- **Headless render service** (`browserless` in `docker-compose.prod.yml`, BACKLOG 14.4). Left out.
  In compose it sits on its own network that only `worker-assets` can reach. Render's private
  network is shared by every service in the region, so a browser there could reach the database
  and Key Value hostnames. It would also cost $25+/month per environment for a rarely used
  fallback. Without it, website scans that bot protection blocks stay `blocked` and the owner uploads
  images instead ([scan-blocked.md](scan-blocked.md)). To add it later, it needs its own isolated
  environment or an external hosted Browserless with `STUDIO_HEADLESS_RENDER_URL` and
  `STUDIO_HEADLESS_RENDER_TOKEN`.
- **Private ingress.** The Engagement pattern keeps `/api/studio/internal/**` and `/api/metrics` on a
  private load balancer. On Render the web service is public. Both are protected by 256-bit tokens
  compared in constant time (`STUDIO_INTERNAL_SERVICE_TOKEN`, `METRICS_TOKEN`), and Prometheus
  scrapes over the private network. To close them at the edge, use the Cloudflare rule in step 6.
  Render's own IP allow-list for web services needs the Scale plan.

## 1. Create the Render account and workspace

1. Sign up at <https://dashboard.render.com> with the company Google or GitHub account, and turn
   on two-factor authentication.
2. Create a workspace named **PostMind** and choose the **Pro** plan. Pro is needed for:
   - 7 days of Postgres point-in-time recovery (Hobby has 3),
   - `networking.isolation` in `render.yaml` (staging cannot reach production over the private
     network),
   - autoscaling later.
3. Invite DevOps as workspace members.

## 2. Before you start: collect these values

You need them in step 4. Keep them in the password manager, never in a file in the repo.

- From **DevOps**: the AWS KMS key id, its region, and an IAM user's access key limited to that key
  (`kms:Encrypt`, `kms:Decrypt`, `kms:GenerateDataKey`). The Cloudflare account id, and an R2 API
  token for the Studio buckets ([r2-setup.md](r2-setup.md) step 2). For production: the four
  production bucket names.
- From the **Core team**: the Core URL, JWKS URL, JWT issuer and audience, audit URL, and the
  `POSTMIND_SERVICE_TOKEN` Core issued to Studio.
- **Provider and platform keys**: every key in `.env.example` you use. A provider is switched on
  only when its key is set.
- **PagerDuty** Events API v2 routing key and a **Slack** incoming webhook for `#studio-alerts`
  ([monitoring-deploy.md](monitoring-deploy.md)). Use separate ones for staging if you want staging
  alerts to stay out of the production channel.
- The **domains**, for example `studio.postmind.ai` (production) and `studio-staging.postmind.ai`.

## 3. Create the Blueprint

1. In the Render Dashboard: **New → Blueprint**.
2. Connect GitHub if asked, and give Render access to the `postmind-studio` repository only.
3. Pick the repository and branch `main`. The Blueprint path is `render.yaml`.
4. Render lists everything it will create (2 databases, 2 Key Values, 18 services including the 2
   backup cron jobs, 6 environment groups) and asks for the values marked `sync: false`: the
   monitoring secrets and the backup job's bucket and token
   ([r2-setup.md](r2-setup.md) step 7; leave them empty and fill them later if the backup bucket
   does not exist yet, and the job's runs fail until then):

   | Service | Key | Value |
   | --- | --- | --- |
   | `studio-monitoring-staging` | `PAGERDUTY_ROUTING_KEY` | PagerDuty routing key (staging) |
   | `studio-monitoring-staging` | `SLACK_WEBHOOK_URL` | Slack webhook (staging) |
   | `studio-monitoring-production` | `PAGERDUTY_ROUTING_KEY` | PagerDuty routing key |
   | `studio-monitoring-production` | `SLACK_WEBHOOK_URL` | Slack webhook |
   | `studio-backup-storage-<env>` | `S3_BACKUP_BUCKET` | The environment's R2 backup bucket |
   | `studio-backup-storage-<env>` | `S3_BACKUP_ACCESS_KEY_ID` / `S3_BACKUP_SECRET_ACCESS_KEY` | The backup job's R2 token (read on the live buckets, read & write on the backup bucket) |

5. Click **Deploy Blueprint**. The first deploys start at once. Postgres and Key Value come up, and
   the web pre-deploy step creates the schema. App services that need secrets will fail or restart
   until step 4 is done. That is expected.

## 5. R2 CORS and the app URL

Browser uploads go straight to the assets bucket. Add the environment's `APP_URL` origin to that
bucket's CORS rule ([r2-setup.md](r2-setup.md) step 3). Register each OAuth redirect URI above in
the platform's developer portal.

## 6. Custom domains and Cloudflare DNS

For each environment's web service:

1. Render: `studio-web-<env>` → **Settings → Custom Domains → Add Custom Domain**, for example
   `studio.postmind.ai`. Note the `….onrender.com` target Render shows.
2. Cloudflare: select the `postmind.ai` zone.
   1. **DNS → Records**: delete any `AAAA` record for that name (Render does not support IPv6).
   2. **SSL/TLS → Overview**: encryption mode **Full**.
   3. **Add record**: type `CNAME`, name `studio` (or `studio-staging`), target the
      `….onrender.com` host, proxy status **DNS only**. Save.
3. Render: wait until the domain shows the certificate as issued (**Verify** re-checks).
4. Optional, recommended: switch the Cloudflare record to **Proxied**, then add a WAF custom rule on
   that hostname:
   - **block** `URI Path starts with /api/metrics` (Prometheus uses the private network), and
   - **block** `URI Path starts with /api/studio/internal/` **unless** the source IP is one of
     Core's egress IPs.

   Once the custom domain works, set **Settings → Custom Domains → Render subdomain** to disabled,
   so nobody can reach the service round Cloudflare through `onrender.com`. This setting needs
   at least one custom domain.
5. Update `APP_URL` and the redirect URIs in `studio-secrets-<env>` if they changed.

**Disconnect the old Cloudflare Workers build.** Cloudflare has a Workers project named
**postmindstudio** that tries to build this repository as a Worker on every push, and fails.
Studio is not a Worker. In Cloudflare: **Workers & Pages** → `postmindstudio` → **Settings →
Builds → Disconnect**
([Cloudflare docs](https://developers.cloudflare.com/workers/ci-cd/builds/#disconnecting-builds)).
Delete the Worker afterwards if nothing else uses it.

## 7. First deploy: check it

On staging (then the same on production after step 8):

1. **Deploys.** Every service in the environment shows **Live**. In `studio-web-<env>` →
   **Events/Logs**, the pre-deploy step logs `prisma migrate deploy` ("All migrations have been
   successfully applied" or "No pending migrations") and `[seed] system_flags seeded`.
2. **Health.**
   ```bash
   curl -s https://studio-staging.postmind.ai/api/health        # 200
   curl -s https://studio-staging.postmind.ai/api/health/ready  # 200, database + redis up
   ```
   If `ready` reports `redis` down, check the Key Value instance is Available. Studio selects
   Redis DB 3 on the connection, which Valkey supports by default. If it fails, open a Render
   support ticket, because this is UNVERIFIED on Render Key Value.
3. **Migrations and pgvector.** In `studio-web-<env>` → **Shell**:
   ```bash
   sh scripts/render/with-db-url.sh npx prisma migrate status   # "Database schema is up to date!"
   ```
4. **Workers.** Each `studio-worker-*` log shows `studio workers started` with its queue.
5. **Prometheus.** In `studio-monitoring-<env>` → **Shell**:
   ```sh
   wget -qO- 'http://127.0.0.1:9090/api/v1/targets?state=active' | grep -o '"health":"[a-z]*"' | sort | uniq -c
   ```
   Every target is `up`: 1 web target per instance, 1 per worker instance, readiness, Prometheus
   and Alertmanager.
6. **Alert smoke** (tell the on-call first). From `studio-web-<env>` → **Shell**, with the
   monitoring service's internal hostname from its **Connect** menu:
   ```bash
   ALERTMANAGER_URL=http://<studio-monitoring-host>:9093 npx tsx scripts/ops/alert-smoke.ts --severity ticket
   ```
7. **Test generation** (spends real provider money, about one short clip). From the web **Shell**:
   ```bash
   sh scripts/render/with-db-url.sh npx tsx scripts/run-test-project.ts --queue
   ```
   The workers pick it up. The project should reach `READY_FOR_REVIEW`. Then run the R2 smoke test
   in [r2-setup.md](r2-setup.md) step 6 and one real upload from the browser.
8. **Secrets survived the sync.** Open `studio-secrets-<env>` again and check the keys are still
   there. Do the same after your first change to `render.yaml`.

## 8. Promote staging → production

Production runs exactly the commit that passed on staging. Render builds the image for each
service from that commit.

1. Find the commit live on staging: `studio-web-staging` → **Events** (or `echo $RENDER_GIT_COMMIT`
   in its Shell). Check the staging gate for that commit is green ([staging-gate.md](staging-gate.md)).
2. Create a Render API key (**Account settings → API Keys**) and keep it in the password manager.
   Copy the service ids (`srv-…`) of the production services from each service's **Settings**.
   List the web service first.
3. Deploy:
   ```bash
   export RENDER_API_KEY=rnd_…
   export RENDER_DEPLOY_SERVICE_IDS=srv-web,srv-orchestration,srv-assets,srv-publish,srv-scheduled,srv-analytics,srv-library,srv-monitoring
   npx tsx scripts/render/deploy.ts <commit-sha>
   ```
   It deploys the web service first (its pre-deploy step migrates the database), waits until it is
   live, then deploys the rest together, and exits 0 only when all are live. The same thing by hand:
   each service → **Manual Deploy → Deploy a specific commit**, web first.
4. Record the SHA and the previous SHA in the deploy log ([deploy.md](deploy.md)), and watch
   Sentry, the p95 latency, failed jobs and the queue depths for 30 minutes.

Changes to `render.yaml` itself (plans, instances, env groups, commands) reach **both**
environments as soon as they merge to `main`: by default Render syncs a Blueprint on every push to
its branch, whatever the services' auto-deploy setting
([Blueprints](https://render.com/docs/infrastructure-as-code#disabling-automatic-sync)). Review them
as production changes, or set the Blueprint's **Auto Sync** to **No** and press **Manual Sync**
when you are ready. A sync also overwrites dashboard edits that conflict with the file.

## 9. Rollback

Decide as in [rollback.md](rollback.md). If customers could be harmed while it runs, engage the kill
switch first.

- **Fastest:** each service → **Deploys** → the last good deploy → **Rollback**. Render reuses that
  deploy's build, so there is no rebuild. Rolling back from the dashboard turns auto-deploy off for
  the service; turn it back on for staging when you are done.
- **Scripted**, all services, reusing retained builds:
  `npx tsx scripts/render/deploy.ts <previous-good-sha>` with the environment's service ids.
- Migrations are expand-only, so the previous release runs on the newer schema. Never run
  `prisma migrate reset`.
- Render keeps a limited number of builds per service (5 on Hobby). Older commits are rebuilt, which
  takes longer than the 5-minute SLO.

## 10. Scaling

- **More instances:** change `numInstances` for the service in `render.yaml` and merge. For an
  emergency, use the service's **Scaling** page, then copy the value into `render.yaml`, because a
  Blueprint sync puts the file's value back.
- **Bigger instances:** change `plan`. Workers that run FFmpeg (assets, library) need `1c-2g` or
  more; raise a 512 MB worker if its logs show out-of-memory restarts.
- **Database connections:** each instance opens up to `STUDIO_DB_CONNECTION_LIMIT` connections.
  Keep the total, doubled for deploy overlap, under the Postgres plan's limit (100 for `0.5c-1g`,
  200 for `2c-8g`). PgBouncer pooling is off on purpose: Prisma Migrate needs a direct connection,
  and the current total fits.
- Postgres and Key Value plan changes restart them (a few minutes of downtime). Key Value cannot be
  downgraded.

## 11. Backups and restore

- **Postgres PITR.** Render backs up paid Postgres continuously. You can restore to any point in the
  last **7 days on a Pro workspace** (3 days on Hobby)
  ([Render docs](https://render.com/docs/postgresql-backups)). **Recovery → Point-in-Time Recovery
  → Restore Database** creates a **new** instance. It cannot be within 10 minutes of now.
- **Cut over after a restore:**
  1. Verify the new instance:
     `RENDER_POSTGRES_URL=<new internal URL> sh scripts/render/with-db-url.sh npx tsx scripts/ops/staging-gate.ts --restore-check …`
     from the web Shell ([backup-recovery.md](backup-recovery.md)).
  2. Engage the global kill switch. On each of the seven app services, override
     `RENDER_POSTGRES_URL` with the new instance's internal URL and deploy.
  3. In the same hour, change `fromDatabase.name` in `render.yaml` to the new instance and merge.
     Otherwise the next Blueprint sync points the services back at the old database.
- **Logical exports:** **Recovery → Create export** (kept 7 days). Download one before risky
  maintenance.
- **Key Value** is rebuildable; see [backup-recovery.md](backup-recovery.md) "After a Redis loss".
- **R2** has no versioning. `studio-backup-storage-<env>` copies the live buckets into the backup
  bucket every day at 03:30 UTC and ages out copies 30 days after their source was deleted. A
  failed run shows **Failed** on the cron job and sends the workspace's failure notification;
  **Trigger Run** re-runs it. Restore: [backup-recovery.md](backup-recovery.md).
- **Monitoring disk:** Prometheus history only. Losing it loses graphs, not alerts.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| Pre-deploy fails with `Missing required environment variable RENDER_POSTGRES_URL` | The service lost its `fromDatabase` link. Re-sync the Blueprint. |
| Pre-deploy fails in `prisma migrate deploy` | Fix forward with a new migration ([rollback.md](rollback.md#database-migrations)). The old release keeps serving. |
| A worker deploy never becomes Live | A private service must open a port. `METRICS_TOKEN` is missing, so the metrics listener is off. Check `studio-metrics-<env>` is linked. |
| `Local key provider is not allowed in production; set KMS_KEY_ID` | `KMS_KEY_ID` is missing from `studio-secrets-<env>`. |
| `StudioTargetDown` for every worker | The monitoring service's hostname variables are stale. Sync the Blueprint, then restart monitoring. |
| Too many Postgres connections during deploys | Lower `STUDIO_DB_CONNECTION_LIMIT` or raise the Postgres plan (section 10). |
